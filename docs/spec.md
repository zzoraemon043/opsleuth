# opsleuth 規格

自動還原「opcode 被重新編號」的 Lua 位元碼，輸出標準位元碼交給現有反編譯器（unluac、luadec、ljd）。

## 1. 要解決的問題

很多手遊會把 Lua VM 的 opcode 順序打亂、改壞檔頭，讓現成反編譯器無法使用。目前只能手動逆向 VM 找映射表，每款遊戲都要重做一次。

opsleuth 的目標：只給位元碼檔（可選擇再給遊戲的原生程式庫），自動推出映射表。

## 2. 範圍

| 版本 | 第一版 | 備註 |
|---|---|---|
| Lua 5.1 | ✅ | 手遊最常見，38 個 opcode |
| LuaJIT 2.1 | ✅ | 第二常見，97 個 opcode（新版另有 7 個位元運算）；2.0 編號不同，之後再加 |
| Lua 5.2／5.3／5.4 | 之後 | 格式相同思路，逐版加 |

不做：解密（XXTEA、AES 等先由使用者自己解開）、反編譯本身、繞過反作弊。

## 3. 三種推導來源（由強到弱，可疊加）

### 3.1 原生程式庫的 opnames 表
- 掃描 .so／.dll 找 `luaP_opnames` 這類字串指標陣列（"MOVE"、"LOADK"…），依陣列順序直接得到映射。
- 支援 ELF、PE；沒 strip 時幾乎一定成功。
- 找不到時退回 3.2。

### 3.2 已知明文比對
- 使用者提供部分已知源碼（例如遊戲裡沒被加密的 config、或公開的第三方函式庫）。
- 用標準 luac 編譯，和遊戲位元碼逐函式對齊：指令數相同、常數表相同時，逐指令取得對應關係。

### 3.3 只靠位元碼的約束求解（核心）
每個未知 opcode 是一個變數，可能值是標準 opcode 集合，用約束逐步刪減：

- **運算元合法性**：LOADK 的 Bx 必須小於常數數量；CLOSURE 的 Bx 必須小於子函式數量；GETGLOBAL 的常數必須是字串；暫存器編號不能超過 maxstacksize。
- **控制流**：跳躍目標要落在函式內；FORPREP／FORLOOP 成對且跳躍距離互相對應；TFORLOOP 後面接 JMP（5.1）。
- **結構固定點**：每個函式最後一條一定是 RETURN；CLOSURE 後面跟的 MOVE／GETUPVAL 數量等於子函式 upvalue 數。
- **統計**：MOVE、GETTABLE、CALL 等出現頻率排序在不同遊戲間很穩定，用來排列候選順序。
- 求解：約束傳播＋回溯搜尋；全部檔案共用一組映射，檔案越多解越唯一。
- 驗證：套用映射後用內建的位元碼驗證器（模擬堆疊高度）檢查全部函式，再試跑反編譯器，成功率要達 100%。

## 4. 檔頭修復

自動偵測並修正常見的修改：簽名被改、版本位元組被改、size_t／指令大小欄位被清零、大小端旗標錯誤。修改內容列進報告。

## 5. 介面

```
opsleuth detect  <檔案或資料夾>              # 判斷版本、檔頭異常
opsleuth solve   <資料夾> [--lib libgame.so] [--known 已知源碼資料夾] -o map.json
opsleuth apply   <資料夾> --map map.json -o 輸出資料夾   # 產出標準位元碼
opsleuth verify  <輸出資料夾>                 # 驗證器＋反編譯試跑
```

map.json 內容：版本、映射表、每個 opcode 的信心度與證據來源、未決的 opcode 清單。

## 6. 技術選擇

- Python 3.10＋，純 Python，零相依；求解器與 ELF／PE 解析都自己寫。
- 反編譯試跑選用：本機有 Java 就呼叫 unluac。

## 7. 測試與範例

- 💣 倉庫只放**自己用標準 luac 編譯**的範例，不放任何遊戲的位元碼、金鑰或還原結果。
- 測試產生器：拿開源 Lua 專案編譯，隨機打亂 opcode、改壞檔頭，檢查能否 100% 還原。
- 指標：模型沒看過的專案、100 個檔案以上時，Lua 5.1 全部 opcode 正確；結果見 README 準確度表。
- 實測結果：結構約束只能唯一決定少數 opcode，大部分靠「約束刪減候選＋學習評分＋全域指派」；四則運算彼此對調是主要剩餘錯誤。

## 9. 法律與公開

- 定位為通用研究工具，README 不提任何特定遊戲名稱。
